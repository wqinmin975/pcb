## 1. S3DA description — resolved by implementing the original rule (Reviewer 2, comment 3; Reviewer 1, comment 3)

**The concern.** The original S3DA of Xu et al. [6] is a *hand-tuned rule-based
volume-threshold* algorithm: the solder volume is obtained by integral
summation and compared against fixed acceptance limits. Our previous
implementation was a decision tree (`max_depth = 6`) trained on all seven
features — a learned proxy, not the published rule. The reviewer was right to
question this.

**What we did.** We implemented the original rule and **re-ran every
experiment** with it:

* `S3DARuleClassifier` (new, `solderbench/baselines.py`) computes the solder
  volume by integral summation (the voxel-count descriptor `vol`) and compares
  it against two **hand-set** acceptance limits, `0.90` and `1.10`, expressed
  as fractions of a nominal reference volume.
* The nominal reference volume is calibrated as the **median volume of the
  training features only** — unsupervised, using no class label. The rule has
  no trained parameters, so its decision is deterministic and identical for
  every seed.
* Because the published rule thresholds volume alone, it can only emit the
  labels {good, insufficient, excessive}. Bridging and collapse are not volume
  defects, so the rule **never** predicts them.

**All S3DA numbers in the manuscript (Tables 4, 5 and 6) now come from this
original hand-crafted rule implementation.** The learned tree proxy is retained
in the repository (`get_s3da_tree_proxy()`) for reference only and is *not*
used for any reported number.

**Reported numbers (original rule):**

| | seed 42 | five seeds (mean ± std) |
|---|---|---|
| Accuracy | 0.5600 | **0.5632 ± 0.0091** |
| macro Precision | 0.4160 | 0.4245 ± 0.0069 |
| macro Recall | 0.5600 | 0.5632 ± 0.0091 |
| macro F1 | 0.4588 | 0.4636 ± 0.0075 |
| CV accuracy | 0.5726 ± 0.0301 | 0.5675 ± 0.0376 |

For reference, the *learned tree proxy* (repository only, not reported in the
paper) reaches 0.9131 ± 0.0156 accuracy over the same five seeds — which is
exactly why the distinction matters: the proxy is ~0.35 accuracy stronger than
the published rule, and conflating them would have overstated the industrial
baseline.

**Anticipating the follow-up question "are the two limits tuned?"** We ship a
sensitivity sweep, `python examples/s3da_threshold_sensitivity.py`, which
evaluates the rule over five seeds for limits (0.70, 1.30), (0.80, 1.20),
(0.85, 1.15), (0.90, 1.10) and (0.95, 1.05). The rule's mean accuracy ranges
from **0.3163** to **0.5632** across that sweep; i.e. it remains far below
every learned method (the weakest learned method, kNN, is at 0.9253) for
*every* setting. The qualitative conclusion is therefore insensitive to the
choice of limits.

**Consequential text corrections.** Because B1 changed, we also corrected the
claims that depended on the old number:

* ~~"S3DA is a strong baseline … volume alone carries most of the class
  signal"~~ → the rule is far above the 0.20 chance level but far below every
  learned method; volume alone is *necessary but not sufficient*, and its zero
  recall on bridging/collapse is structural, not an implementation defect.
* ~~"kNN remains statistically tied with S3DA"~~ → removed; every learned
  method, including kNN at 0.9253, beats the rule by more than 0.36 accuracy
  (many times the inter-seed std).
* ~~"the S3DA rule … reaches 0.8960 accuracy using volume only"~~ → 0.5600 at
  seed 42 (0.5632 ± 0.0091 over five seeds).

## 2. Voxel size (consistency check)

The manuscript has always used **δ = 0.01 mm**, and so does the code
(`solderbench/features.py`: `VOXEL_SIZE = 0.01`). We re-checked the whole
manuscript: **no 0.05 mm value appears anywhere**. The value 0.05 mm was from
an external template and was never adopted. The manuscript states the voxel
edge explicitly in the feature-table caption and in the `vol` row
(`vol = N_vox · δ³`, δ = 0.01 mm, units mm³).

## 4. `load_dataset()` — what is implemented and what is not (Reviewer 1, comment 4)

The manuscript now states, at the end of §3.1:

> `load_dataset()` provides a software hook for external real-world point-cloud
> input. Real-world data acquisition, joint segmentation and pre-processing
> functions are **not** implemented within this package; users must supply
> pre-segmented solder-joint point clouds (or their own `X, y` feature matrix)
> at this hook, after which every downstream experiment runs unchanged.

The same caveat is now in the package docstring (`solderbench/data.py`) and in
the README. What the package *does* provide is: the hook, the seven-feature
extractor, and the full evaluation pipeline — all covered by unit tests.

## Additional clarifications added during this revision

* **Comparison conditions (Reviewer 2, comment 3).** All six methods use the
  identical stratified 7:3 split, the same seven-feature input, and the same
  5-fold CV protocol. This is now stated explicitly.
* **Statistical tie wording (§4.2).** "Statistically tied" is now defined:
  *the observed accuracy gap is smaller than the inter-seed standard
  deviation* (RF − GradientBoosting: gap 0.0053, inter-seed std 0.0065).
* **Limitations (§6).** Added: *all benchmark experiments in this manuscript
  are based exclusively on synthetic data; the absolute accuracy values cannot
  be directly transferred to industrial real-world inspection* — only the
  relative ordering under a controlled, identical protocol should be read as a
  result.
* **Reproducibility (Reviewer 1/2, software usability).** Pinned dependency
  set in `requirements.txt` (Python 3.13, NumPy 2.5.2, SciPy 1.18.0,
  pandas 3.0.6, scikit-learn 1.9.0, Matplotlib 3.11.1), a `Dockerfile` for a
  one-command reproducible image, and a rewritten README (all 15 generator
  parameters, five-seed results, robustness ablations, reproduction commands
  and runtimes, archival citation). Archived on Zenodo, concept DOI
  `10.5281/zenodo.22959192` (always resolves to the latest release).
